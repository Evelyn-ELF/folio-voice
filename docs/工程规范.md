## 1. 适用、依据与冲突处理

1. 新增或修改工程规范时，必须登记发布机构、标题、版本、官方链接、适用主题、项目落实方式和证据。优先采用正式标准，其次采用维护方官方规范与文档；博客、搜索摘要和工具默认值不作为规范来源。
2. 以下 ISO/IEC/IEEE 标准当前核查范围为官方公开目录、状态及摘要，未取得付费全文。它们用于确定工程活动与信息组织的依据；不据此杜撰条款号、逐条要求或宣称项目已通过标准符合性认证。需要逐条符合性评估时，先取得合法全文并补充条款映射。
3. 公开技术规范按列出的版本使用。版本更新先评估兼容性，不自动替换正在使用的工程基线。首次引入、升级或规范状态有疑问时复核官方来源，无须每次改文案重复联网。
4. 规范要求、项目约定、产品需求和实现事实分别标识。本项目的目录布局、重试次数、单机部署、声音听审标准等属于项目决策，不声称由 ISO 或某工具强制规定。
5. 规范适用性存在冲突时记录影响和处理理由。用户业务需求决定产品范围；协议实现不得以业务偏好为由虚报符合性。候选技术仅在实际验证后进入依赖锁和支持矩阵。
6. 标准用于检查内容和行为，不能仅在文末列参考文献。设计评审、代码评审和测试报告应引用S来源编号与N规则编号，标明落实位置及未验证事项。

文档分工和冲突处理以[根入口](../README.md)为准。本文规定方法，产品行为只在系统设计定义，验证结果只在开发任务登记。

## 2. 文档编写与维护

依据：S01、S02、S03、S04。以下为项目落实规则。

| 文档类型 | 必备信息 | 检查方式 |
|---|---|---|
| 需求说明 | 编号、来源、范围、前提、需求陈述、优先级、验收条件、变更历史 | 每条必需需求有对应设计和验证项 |
| 系统设计 | 文档控制、目标、边界、利益相关方、关注点、视点与视图、模块、数据、接口、运行、部署、安全、质量、决策、风险及追踪 | 各视图术语一致；接口和数据相互对应；风险有关闭条件 |
| 实施计划 | 关联需求/设计、任务、依赖、修改范围、验证命令、完成条件 | 可逐项执行，不能只有阶段口号 |
| 测试计划与报告 | 目标、范围、环境、用例、预期、实际、证据、缺陷、限制和结论 | 未运行、受阻、失败、通过分开记录 |
| 部署/运维手册 | 前提、准确版本、配置、操作步骤、预期结果、失败处理、备份恢复及升级回退 | 在指定干净环境演练 |
| 决策记录 | 背景、选项、选择、理由、代价、状态、受影响需求和复核条件 | 新决定不覆盖旧记录；记录替代关系 |
| 任务状态 | 当前状态、已完成证据、未完成事项、入口、下一步、适用约束 | 与Git和测试记录一致，不复制第二套设计 |

文档统一使用中文，技术标识可保留英文。标题层级连续；引用使用可追踪链接；日期和版本明确。未经验证的经验不写成验收事实；文档中的示例数据不能冒充真实测试结果。核心文档更新时同步入口及章节引用。

日常开发只维护根入口列出的四份活动文档。上表是信息要求，不要求为每类另建文件：实施计划和进度进入开发任务，决策进入系统设计，实际报告作为验证附件，发布时提供面向使用者的操作手册。

每条规则保留一个完整定义，其余位置使用稳定锚点引用。正文先说明目的和行为，再给字段和异常；长流程用步骤，表格用于比较与索引。章节编号连续，需求/用例等稳定ID不作为章节编号。

### 2.1 文档随开发维护的流程

本流程依据S02/S03/S04的需求、信息项和变更过程公开范围进行项目裁剪，检查与证据依据S05/S06；以下步骤及工具由项目自行规定，不宣称是标准原文要求。对应N02/N03/N20/N26。

1. **确定归属与影响**：需求或行为修改进入系统设计，方法进入本文件，验证方法进入验证计划，执行进度进入开发任务。先列受影响的需求、接口、数据、状态、预算和用例；纯排版修改只检查结构、引用和语义是否保持。
2. **原位修订**：修改对应章节，删除失效规则，必要时按阅读顺序调整章节。不要在末尾不断追加补充说明，不用日期或“最新”字样覆盖前面的冲突。活动文档呈现当前有效设计，修改历史由Git和关联评审记录保存；尚未提交的工作不得声称已有提交记录。
3. **同步关联项**：按影响范围更新契约、验证项、任务及必要的权威依据；接口和质量策略变化同时检查正常路径、失败路径及证据失效范围。不强求每次都修改四份文档，也不以更新任务状态替代设计修改。
4. **检查与审查**：执行下节命令，然后逐项完成语义审查。检查发现问题时修正原处；相关冲突未解决前不继续受影响实现，无关工作可继续。
5. **记录并关闭变更**：在相关F任务或PR/本地评审中记录影响范围、命令及结果、语义结论和剩余问题。相关文档已同步、机械检查通过、语义冲突已处理，才算变更完成；未完成部分保持显式状态。

稳定编号不得因重排而改变或复用。需求废止时保留编号及废止理由，关联验证项明确处置；新增编号按序追加。新增独立文档必须先明确用途、维护者和与现有四份文档的关系，同步入口与检查范围，不能另建并行规范。一般修改优先在现有文档内完成。

### 2.2 机械检查命令与边界

在仓库根目录运行；文档检查仅使用Python标准库，默认只输出结果，不修改文件：

```sh
python3 tools/check_documents.py
```

需要保留本次记录时，显式指定附件路径：

```sh
python3 tools/check_documents.py --output docs/validation/文档检查.json
```

[检查器](../tools/check_documents.py)检查活动文档集合、章节层级与编号、表格结构、显式锚点、内联本地链接、稳定编号的唯一归属和引用、需求R与验证V的双向映射。编号数量随合法新增条目变化，不固定为当前数量；结果包含输入散列和检查时间，后续修改后须重新运行。退出码0表示所列机械检查通过，1表示发现问题。

活动文档使用内联Markdown链接及显式HTML锚点；新增链接或编号语法时先扩展工具与测试。检查器不扫描归档、代码围栏内的示例及验证附件正文，不联网核验外部来源，也不能判断自然语言是否矛盾、业务规则是否正确或Schema是否符合设计。

机器契约或结构样例发生变化时，在安装了[锁定校验依赖](validation/契约校验环境.txt)的隔离Python环境运行：

```sh
python tools/validate_design_contracts.py
```

该命令只校验Schema及结构正反例；文档与契约的字段、枚举和业务语义仍须人工逐项对照。检查器或其规则变化时，同时运行检查工具自身的回归测试：

```sh
python3 -m unittest discover -s tools -p 'test_*.py'
```

工具编码依据S08，回归组织依据S20，Schema校验依据S29/S30。建立CI时将这些适用命令接入，失败阻止合并；在此之前由每次实际开发工作执行，不宣称当前已有自动CI拦截。

### 2.3 语义审查清单

- **归属与重复**：规则是否只有一个完整定义；其他位置是否引用正确；是否出现第二套任务状态。
- **一致性**：是否清除旧表述；需求、接口、状态、权限、预算、质量门槛与机器契约是否相容；正常和失败路径是否都成立。
- **可验证性**：变更是否有适用验证项；证据失效是否重新打开任务；是否将计划或模拟结果误写成真实通过。
- **可读性**：信息是否放在读者需要的位置；术语是否统一；长表和段落是否应拆分；关键规则和下一步是否容易找到。

语义结论写明“审查范围、发现及处置、未决项”，由实际修改者或评审者负责。没有独立评审者时如实记录自审；不得把自动检查结果标成已完成语义审查。不为每次修改新增一份规范或审查说明文档。

## 3. 编码、接口与评审

依据：S01–S07的架构、需求、生命周期与验证范围，以及S08–S12、S29的技术规范。以下模块边界、同步流程和检查门槛是项目约定，不冒称标准指定的目录结构或开发方法。对应N06–N08、N27–N29。

### 3.1 编码与评审基线

- Python遵循PEP 8，公共边界标注类型；Ruff和类型检查器作为执行工具，准确版本及规则在工程初始化时锁定。格式宽度等配置差异应记录为项目裁剪。
- TypeScript启用`strict`；禁止以无依据的`any`或关闭检查代替修复。前端错误和用户提示使用中文。
- 核心领域模块不依赖Web或模型框架；输入验证、状态转换与持久化边界可测试。外部输入不拼接为shell命令，敏感内容不进入日志。
- 接口必须提供机器可读契约、认证要求、输入输出、异常语义和兼容性规则。HTTP响应遵循S11；错误体遵循S12，禁止以HTTP 200掩盖失败。
- 版本、依赖、配置及模型修订固定；变更有追踪记录。第三方组件采用前阅读其官方接口及许可证；不得将候选工具写成已验证支持。
- PR或本地等价评审记录列关联需求、规范编号、影响、测试及例外。格式检查只能证明配置规则通过，不能证明软件正确或符合所有标准。

开发按需求编号关联设计、代码、用例与发布；关键决策统一进入[系统设计的决策记录](系统设计.md#adr)。框架用法读取对应官方资料，不能把未经验证的示例当作运行事实。

缺陷先固化可揭露错误的用例；声音缺陷另存音频证据。核心逻辑、数据迁移和安全边界进行代码评审；禁止用模拟模型通过冒称MLX实测通过。

CI使用可公开素材，运行静态、单元、契约、集成、受影响的界面测试和镜像构建。真实Mac硬件验证独立执行，外部不可信代码不访问私人运行器或凭据。依赖更新经评审和回归后锁定；运行中的制作版本不自动升级。

<a id="code-boundaries"></a>

### 3.2 模块边界与规则集中定义

依赖关系按[系统设计的模块职责](系统设计.md#modules)与[代码组织](系统设计.md#code-layout)实现：界面通过业务接口操作；核心业务不依赖Web框架或模型供应商；供应商差异留在适配器；执行器通过app API提交结果，不能绕过应用直接写数据库。新增功能先确定归属，不能为方便调用穿透边界或引入循环依赖。

状态转换、错误码、预算和质量裁决分别由明确模块或版本化配置负责。调用方复用公共接口，不复制整套判断、散落同义常量，也不把不同业务规则强行塞进一个通用工具类。不可避免的跨语言副本必须由生成流程或一致性校验维护。

F03固定允许的依赖方向、检查工具及命令；F04用实际模块验证越层访问和循环依赖能被拦截。目录分开或类型检查通过，均不等于架构边界已得到验证。

<a id="code-document-consistency"></a>

### 3.3 代码、契约与文档同步

系统设计说明预期行为与理由；机器契约表达结构、字段和枚举；实现负责执行，测试提供行为证据。各自只维护对应信息，不设“代码总是正确”或“文档总是正确”的优先规则。

接口结构优先从选定的Schema/OpenAPI生成类型和客户端，或通过自动一致性检查约束；F03明确源文件、生成命令及输出位置。生成文件不得手工修改后脱离源契约。数据库迁移与接口结构通过适用测试核对，不假定二者可直接互相生成。文档引用结构契约，重点说明行为、失败条件和取舍，避免再复制完整字段清单。

一次变更围绕一个明确目的，将受影响的代码、契约、测试和文档作为同一可评审变更交付。纯内部重构不要求机械修改产品文案，但需说明外部行为未变及其验证；需求变更不能用“只改代码”交付。

| 不一致类型 | 处理方式 |
|---|---|
| 实现偏离已确认需求或设计 | 修实现，补能揭露偏差的回归用例；不为迁就缺陷改写验收条件 |
| 需求或设计正式变化 | 同步设计、契约、实现、验证条件及受影响任务，处理旧证据失效 |
| 文档错误或过期 | 根据已确认需求和实际证据修正文档；不能把偶然实现写成合理设计 |
| 证据不足或存在争议 | 关联原任务记录冲突与影响范围，暂停受影响修改；无关工作继续 |

例如修改自动修复次数，先改唯一预算定义，核对Agent和执行器共享的计数，再验证超限、重启及重复请求不会绕过上限，最后同步设计说明与适用用例。不能只替换某处数字，也不能用格式检查证明行为正确。

<a id="change-completion"></a>

### 3.4 自动检查与变更完成条件

按变更影响选择检查，不以每次全量重测代替风险分析，也不为通过检查临时关闭规则或降低门槛：

| 变更范围 | 必需检查与证据 |
|---|---|
| 所有开发变更 | 文档机械检查、相关文档同步和语义审查、受影响文件的清理检查；列明涉及的R/F编号及不适用项理由 |
| 代码与依赖关系 | 锁定的格式、静态和类型检查；受影响的依赖边界检查；代码评审 |
| 接口、枚举、配置和迁移 | 契约校验、生成结果一致性；适用的兼容性、迁移和运行行为测试 |
| 业务规则与缺陷修复 | 能揭露目标错误的正反例，以及受影响的集成、恢复或端到端测试 |
| 模型、提示、检测或质量策略 | 按验证计划补充真实评估并处理资格失效；模拟测试不能替代 |

F03定义本地与CI共用的命令、锁定版本和必需检查；F04提供运行证据及故意违规的负例。接入CI后，必需检查失败不得合并；启用分支保护等远端限制前，不能宣称已实现强制拦截。没有CI时仍须执行本地适用检查并保存结果。

变更完成前，修改者或评审者必须逐项回答：

1. 修改是否符合模块职责，是否新增了重复规则？
2. 行为、权限、状态和失败处理是否符合需求与契约？
3. 相关文档是否同步，证据是否仍适用，未决冲突是否已处理？
4. 哪些检查实际执行并通过，哪些未执行或不适用，理由是什么？
5. 本次新增、替代及废弃文件是否已按[文件清理规则](#file-maintenance)处置，引用与必要证据是否保留？

将答案、实际命令和证据位置写入相关F任务或PR/本地评审，未解决问题明确保留。适用检查通过且上述问题有可核查结论才可标完成；CI全绿不能替代设计、代码与语义审查。

### 3.5 局部整理与技术债

修改时检查重复逻辑、职责混杂、过长流程及隐藏副作用，优先整理当前影响范围；不夹带大规模无关重构，不为假想需求提前建设通用框架，也不以文件行数或覆盖率单一数字判断代码质量。

暂不能解决的问题记录到相关F任务，写清位置、影响、暂缓理由、责任角色、处理触发条件和验证方式。影响正确性、安全、数据完整性或本次必需验收的问题不能仅标技术债后放行；清理完成后补证据关闭，不另建第二套待办。

<a id="file-maintenance"></a>

### 3.6 文件随开发清理

依据用户持续整理要求，以及S03/S04的信息项与维护过程公开范围，纳入N29的变更完成条件；以下删除与归档方式为项目约定。

- **触发与范围**：新增或替代文件、重构、实验结束及每次变更交付前，检查本次涉及的文件和生成目录；发现明确废弃文件及时处理，无需等待用户再次提醒。不在无变化时反复全仓扫描。
- **删除**：已无用途且可再生的缓存、临时文件、废弃构建产物直接清理；确认不再使用、无追溯价值的重复文件删除。仍供运行使用的文件不清理；生成目录按需加入忽略规则，不能只靠忽略隐藏垃圾。
- **归档**：有决策、缺陷或历史证据价值的旧内容移入archive，更新归档说明并保留原路径信息。批量历史资料优先压缩；核对成员与逐文件散列一致后才删除展开副本，避免长期保留两份。
- **核实用途**：删除前检查代码、脚本、配置、文档及测试引用和运行用途；仅搜索不到引用不能证明无用。保留有效迁移、依赖锁、测试素材、实际验证证据及必要回退资料。用途不明或含用户未提交工作时先保留，在原F任务记录待核实项；私人素材和运行数据按系统设计的保留与清理规则处理。
- **同步与验证**：同步入口、路径及构建/测试配置，执行文档检查和受影响的实际检查；压缩归档另验完整性。清理范围、理由、结果与未决项记入原任务或评审记录，不新增清理台账。检查工具不能自动判定文件是否无用。

<a id="testing"></a>

## 4. 测试与证据记录

依据：S05、S06；以下为项目记录格式及放行约定。

每个测试用例至少记录：`用例ID、需求ID、风险、前置条件、环境/版本、输入及散列、操作步骤、预期结果、实际结果、状态、证据位置、执行者、时间、缺陷ID`。

测试计划记录层级、范围、排除项、资源、进入/退出条件及风险；报告记录执行汇总、偏差、未解决缺陷和验收限制。覆盖率数字必须说明分母，模拟执行器、真实推理、人工听审和真机验收分别汇总。

1. 单元测试覆盖文本与范围变换、状态不变量和缓存失效；负例必须能揭露目标错误。
2. 契约测试覆盖接口、认证、能力、版本、幂等及过期租约。
3. 集成测试覆盖数据库、制品、执行器、迁移与恢复；端到端测试覆盖用户操作和下载结果。
4. 故障测试覆盖进程退出、休眠、网络中断、磁盘不足、损坏缓存和重复提交。
5. 真实模型质量、开发评估听审、Readest设备测试与逐件兼容匹配独立出具证据；自动策略先按真实听审标定。日常交付不要求消费者全量听审。
6. 任何测试阈值须标明来源：标准规定、用户验收要求或项目工程目标。没有权威依据的百分比不包装成行业硬指标。
